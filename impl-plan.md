## US-107 — List recent runs with GET /api/runs

This plan covers user-approved requirements FR-13 to FR-16 and US-107 AC-01 to AC-07 (with the approved defaults), the user-approved architecture, and design-review decisions D1 to D4 (all answered YES by the user, relayed by the coordinating agent; see `design-review.md`, findings US107-F1 to F6). It is a backend-only, read-only change: no UI, no new dependency, no `pom.xml` change, no change to `POST /api/runs`, `GET /api/runs/{id}`, `/api/health`, static files, `PORT`, or `RUN_DURATION_MS`. The IDs `US-107 AC-nn` are prefixed because plain AC-01 to AC-07 belong to earlier stories.

Settled design inputs that tasks must follow:

- **Ordering:** sort a snapshot of `runs.values()` by `startedAt` descending, then by a per-run `long sequence` (from a new `AtomicLong`, assigned in `start()` after validation, final field) descending. - **Clock seam (D1):** package-private `ExecutionService(Duration, java.time.Clock)`; `start` uses `Instant.now(clock)`; the public no-arg and existing `ExecutionService(Duration)` constructors use `Clock.systemUTC()`.
- **`limit` rules (approved defaults, D3):** absent or empty query gives 20; split the raw query on `&` then the first `=`; decode names with `URLDecoder` (UTF-8); a segment with an undecodable name is skipped; names are case-sensitive; the first `limit` segment decides; valueless (`?limit`), empty, malformed-escape, or undecodable value is invalid; the decoded value must be ASCII digits only (not `Character.isDigit`); drop leading zeros; zero remaining or more than 3 remaining digits is invalid without parsing; otherwise `parseInt` and require 1..100. `05` is accepted (unlike `RUN_DURATION_MS`; do not copy `RunDurationConfig.parse`). One exception type and one fixed message: `limit must be a whole number from 1 to 100.` The rejected input is never echoed.
- **405 (D2):** new overload taking `Allow` and message separately, `Allow: GET, POST`, message "Use the GET or POST method for this endpoint."; for HEAD send `sendResponseHeaders(405, -1)` and write no body. The existing one-argument helper is untouched (other endpoints stay byte-for-byte the same).
- **`handleListRuns`:** the `try/catch (IllegalArgumentException)` wraps only the `parseLimit` call and answers `sendJson(400, jsonError(INVALID_LIMIT_MESSAGE))`. It never reads a body and never calls `start`.
- **Test conventions:** tests assert the literal message text, not the constant; use JUnit 5 and the existing `HttpClient` setup; any test that needs a completed run polls with a deadline (as US-105 did), no fixed sleeps.
