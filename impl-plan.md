## US-106 — GET /api/stats run statistics

This plan covers user-approved requirements FR-13 and AC-26–AC-35, the user-approved architecture, and the design-review decisions in `design-review.md` (US106-F1 agreed by the human; Low findings F3, F4, F8 accepted as test-writing and documentation notes; F7 status-line update approved). The story source is the user-provided chat story; no Jira/MCP retrieval is claimed. It is a backend-only, read-only change: no browser UI, local-storage, `POST /api/runs`, `GET /api/runs/{id}`, outcome, duration, `main`, or `pom.xml` change, and no new dependency (Java 17, Maven, JUnit Jupiter already in test scope). Earlier story sections above are unchanged. Existing tests are not edited; new tests are added to `ExecutionServiceTest` and `DashboardServerTest`.

Settled design inputs that tasks must follow:

- `ExecutionService` gets a public nested record `RunStats(long inProgress, long passed, long failed)` with derived `long totalRuns()` returning the sum (the AC-30 invariant is structural), and `public RunStats stats()`: one pass over `runs.values()`, one volatile read of `completedAtNanos` per run into a local, exactly one bucket per run. No new fields, counters, or locks.
- Status mapping is extracted into `private static String statusOf(long endNanos, String outcome)` on `Run`. It takes the already-read value and never re-reads the volatile field. `toResult()` keeps exactly one read feeding status, duration, and failure details (US106-F1). `stats()` does not call `toResult()` (it would format `startedAt` and call `System.nanoTime()` per run, US106-F2).

Non-GET (POST, PUT, DELETE, PATCH, HEAD) goes through `sendMethodNotAllowed(exchange, "GET")` before any service call. Body: `{"totalRuns":N,"inProgress":N,"passed":N,"failed":N}` by string concatenation, fixed order, no whitespace. `send`, `sendJson`, `sendMethodNotAllowed`, `quote`, and catch blocks are unchanged.
- Test-writing notes (design review): deterministic In Progress uses `ExecutionService(Duration.ofSeconds(10))` with no sleep; completion is awaited by polling with a deadline (about 3 s, about 10 ms interval), never fixed sleeps; the transition assertion is guarded by measured elapsed time (US-105 pattern); the 413 body is only modestly over 4096 bytes (for example 5000); the HEAD test uses `method("HEAD", BodyPublishers.noBody())` with `BodyHandlers.discarding()` or `ofString()`, asserts status 405 and `Allow: GET` only (no body or `Content-Length`), and carries a short comment about the expected JDK content-length warning; the 50-run concurrency test is a sanity check only (may pass vacuously if runs finish first, accepted).
- Conventions: tests use try-with-resources for `ExecutionService` and `DashboardServer`, real server on port 0, the existing `get` helper pattern; the package-private `ExecutionService(Duration)` constructor is the only timing seam.
