## US-105 — Configure the simulated test run duration

This plan covers user-approved requirements FR-12 and AC-20–AC-25, the user-approved architecture, and design-review decisions D1–D5 (approved by the user, as relayed by the coordinating agent; see `design-review.md`). The story source is the user-provided chat story; no Jira/MCP retrieval is claimed. It is a backend startup-configuration change only: no UI, API, report-format, `PORT`/port-argument, or `pom.xml` change, and no new dependency (Java 17, Maven, JUnit Jupiter 5.11.4 already in test scope). Earlier story sections above are unchanged.

Settled design inputs that tasks must follow:

- `RUN_DURATION_MS` unset or blank means 1400 ms. The value is stripped with `String.strip()`, then must be 3 to 5 ASCII digits only, with no leading zero, from 100 to 10000. `+100`, `0100`, decimals, exponent notation, signs, text, and over-range values are rejected. No `NumberFormatException` may escape (length check precedes `Integer.parseInt`).
- A rejected value prints exactly `RUN_DURATION_MS must be a whole number from 100 to 10000.` to stderr, exits with code 2, and does so before `new DashboardServer(...)`, because that constructor binds the port.
- The raw value is not echoed. Tests assert the literal message text, not the `RunDurationConfig` constant (F10).
- Subprocess tests follow the F4 conditions: classes from `DashboardServer.class.getProtectionDomain().getCodeSource()`, `java.home/bin/java`, explicit port argument, explicit `RUN_DURATION_MS`, output to temp files, `waitFor(timeout)` with `destroyForcibly()` in `finally`, JUnit `@Timeout`, and a trimmed-stderr-line assertion.

### US-105 follow-up story to record (not in scope, do not implement)

- **Title:** Recover stale "In Progress" cases after a page reload or close during a run.
- **Problem:** `app.js` saves a case as "In Progress" before the run request and nothing resets it on page load, so a reload or close mid-run leaves the case showing "Running..." with the Run button disabled. Longer durations (up to 10000 ms, about seven times the default window) make this more likely (design-review F6/D4).
- **Why separate:** it needs a browser UI change, which US-105 excludes. US-105 only adds the README caution (task 9).
- **To do:** raise it through the requirements phase as its own story (for example, reconcile stale "In Progress" cases on load, with a decision on how to treat a run whose server-side state is unknown).
